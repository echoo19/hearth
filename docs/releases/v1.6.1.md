# Hearth v1.6.1

A repair release. The tester in v1.6.0 could not open your game at all once it
was packaged, the tester that could open one did not know how to play it, and
the agent's own words were being shown to you with the punctuation still in.

## The tester works in the installed app

In every installed build of v1.6.0, pressing **Play** on the Tester tab ended
the session about nine milliseconds later with a message reading `The "path"
argument must be of type string or an instance of URL. Received undefined`,
whatever your game was. A perfect game failed identically.

The desktop app ships as a single bundled file, and the format it is bundled
into has no way to tell a module where it lives. The module that drives the
browser asked anyway, at load time, and threw before your game was ever opened.
Nothing about that was visible while developing, which is why it shipped: run
from source it works, because there the question has an answer.

The same fault was waiting in two other places and both are fixed by the same
change: making a new game from a template, and exporting a game for the web.

A module that cannot work out where it lives is now allowed to carry on without
one, and if the tester ever fails to start again it says so in its own words
rather than handing you the error underneath.

## The tester plays more like a person

It could only ever hold an input down. There was no way for it to press a key
and let go, so on a racing game it leaned on a steering key, span in circles,
and wrote up that the controls were broken and the game unpleasant to play.
Nothing was broken. Nobody plays a racer by holding left.

It can now tap as well as hold, and the two are genuinely different: a tap is
released before it looks again, so it sees what a press did, while a hold stays
down so it sees the game being driven. Alongside that:

- It is told that when something goes wrong, the likelier explanation is that
  it played badly. It has known the game for a handful of turns and you have
  not.
- It may only call a control wrong once it has tried that control both ways. A
  control it only leaned on is one it has not finished testing.
- Before it says what is worth changing, it is shown its own record of which
  inputs it tapped and which it only held, so a complaint about an input it
  never tapped is one it can see through itself.

What it is asked to look for has moved with it: whether there was something to
do and whether you could work out what, whether the game told you how you were
doing, whether anything you did visibly changed it, whether there was anything
after the first thing. Those are questions it can answer honestly without being
good at the game. How a control feels under the fingers is the one thing it is
worst placed to judge, and it is now told so.

It still will not tell you whether your game is fun. It cannot know that.

## The agent's prose reads as prose

Agents write markdown, and the conversation was showing it to you raw: link
syntax with the brackets still around it, code with the backticks still on.

Now it reads as what it was meant to be, including fenced code blocks with the
language and a copy button. Any absolute path an agent names is something you
can press, whether or not it wrapped it in link syntax, and it opens in the
app rather than navigating away.

None of this asks anything of the agent. Nothing was added to any prompt, and a
message written as plain prose reaches you exactly as it always did.

## Smaller things

- The model selector says **Choose a model** rather than **Auto**. It used to
  read as a setting that had been made for you, and a stored choice with no
  model showed the provider's name, so the pill said Claude while which Claude
  was a fact nothing on screen carried.
- The game column lost the close button in its tab strip. The control in the
  top bar already opens and closes that column, and one control is easier to
  find again than two in different places.
